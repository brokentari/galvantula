      551 +  <h2>Rules that keep parallel work honest</h2>               
      552 +  <ul class="rules">                                          
      553 +    <li><b>Frozen tests.</b> When you approve the contract, th
          +e runtime records a hash of each test file and interface file.
          + A check fails if any of those files changes, or if a new <cod
          +e>t.Skip</code> appears.</li>                                 
      554 +    <li><b>Red before green.</b> The architect's tests must fa
          +il against the empty stubs. A test that passes on a stub tests
          + nothing, so the contract gate rejects it.</li>               
      555 +    <li><b>Write scope.</b> Each task node owns a set of packa
          +ge directories. Nodes that can run at the same time must own d
          +ifferent sets. The runtime rejects a diff that touches a file 
          +outside the node's scope. Because no two nodes write the same 
          +file, merges should not conflict.</li>                        
      556 +    <li><b>The architect owns <code>go.mod</code>.</b> Impleme
          +nter nodes run with <code>-mod=readonly</code> and <code>GOPRO
          +XY=off</code>, so they cannot add dependencies. A node that ne
          +eds a new dependency fails with that reason, and the planner h
          +andles it in a replan.</li>                                   
      557 +    <li><b>Check per node, verify per run.</b> A node's check 
          +runs its own package tests plus a build of the whole module. T
          +he final verify runs the full suite with <code>-race</code>.</
          +li>                                                           
      558 +    <li><b>Agents don't run git.</b> The runtime commits after
          + a check passes. Inside the sandbox, the worktree's <code>.git
          +</code> link points outside, so git cannot work there anyway.<
          +/li>                                                          
      559 +  </ul>

  What the evals are

  The evals are a fixed set of test cases for the factory itself. They don't
  test the factory's code. They measure whether the factory produces correct
  programs.

  Each eval has three parts:
  - spec.md: one paragraph describing a small program, such as "a CLI that
    counts word frequency". This is all the factory gets as input.
  - hidden/: tests that build the program the factory made and check it as a
    black box: they run it with inputs, then check the output and exit code. The
    factory never sees these tests.
  - reference/: my own working answer. It exists only to prove the hidden tests
    are correct.

  After a change to the factory (a new prompt, a different graph, a new model),
  you run all the evals and compare pass rate, cost and time with the last run.
  That tells you whether the change helped or hurt. Without evals, you're
  guessing.

  How they differ from the architect's tests: the factory writes its own tests
  (the architect's frozen tests) and must pass them. But if the architect
  misreads the spec, its tests are wrong in the same way as the code, and
  everything still passes. The hidden tests catch that, because the factory had
  no part in writing them.

  Why "you write these yourself"

  The plan's eval section says: "Five to ten spec prompts, each with acceptance
  tests you wrote yourself." There are two reasons.

  1. Independence. If the same model writes the spec, the tests, and the
     product, they can share the same blind spots. A model can make the same
     mistake in the code and the tests, and then the tests pass for the wrong
     reason. Tests written by a person avoid that.
  2. They define what "correct" means to you. Every spec has gaps, and the tests
     fill them. Here are some choices I made while drafting that you might
     decide differently:
     - wordfreq: "don't" counts as two words, "don" and "t", because only
       letters and digits form words.
     - todo: list --all marks items [ ] and [x]. Marking a done item again is
       not an error.
     - csvq: a column sorts as numbers only if every value in it is a number.
       JSON output values are always strings, even numbers.

     If the factory makes a different, equally reasonable choice, the eval fails
     it. That only means something if the choice the tests require is yours.

  So the three evals I wrote are a starting draft. Read each spec.md and its
  hidden tests, and change whatever doesn't match what you would want. If you
  like, I can go through them with you one at a time, listing each assumption so
  you can approve or change it.
