# rotom

Build a Go TCP server named `rotom`, with its main package at `./cmd/rotom`, that speaks RESP2 and RESP3, the Redis wire protocols, and stores strings in memory. Build it as four packages: the protocol reader and writer in `./internal/resp`, the key store with expiry in `./internal/store`, the command table in `./internal/command`, and the server in `./cmd/rotom`, which wires them together and owns the connections. Add a `README.md` that says how to build and run the server and lists the commands it supports.

## Server

The `--addr` flag sets the listen address and defaults to `127.0.0.1:6379`. Port `0` picks a free port. When the server is ready to accept connections, it prints one line to standard output, `ready HOST:PORT`, with the real address. It serves any number of clients at the same time. Each client may send commands one after another or many at once (pipelining), and the server answers each command in order. On SIGINT or SIGTERM, the server stops accepting, closes all connections and exits with status 0. If it cannot listen, it prints an error to standard error and exits with status 1. A bad flag exits with status 2. All clients see the same data, and the server must have no data race.

## Protocol

A client sends a command as a RESP array of bulk strings, such as `*2\r\n$3\r\nGET\r\n$1\r\nk\r\n`. A client may also send an inline command: one line of words separated by spaces and ended by `\r\n` or `\n`. A blank inline line is ignored. A client sends requests the same way in RESP2 and in RESP3. Bulk strings are binary safe: they may hold `\r\n` and zero bytes. Command names are not case sensitive. Keys and values are case sensitive.

Each connection starts in RESP2. The `HELLO` command switches it to RESP3 or back to RESP2, and the choice holds for that connection only. In RESP2, the server writes these reply types: a simple string (`+OK\r\n`), an error (`-ERR message\r\n`), an integer (`:1\r\n`), a bulk string (`$3\r\nfoo\r\n`), a null bulk string (`$-1\r\n`) and an array (`*2\r\n...`). In RESP3 it writes all of the RESP3 types: those six, with a null written as `_\r\n` in place of a null bulk string, and also a boolean (`#t\r\n`, `#f\r\n`), a double (`,3.141\r\n`), a big number (`(1234567999999999999999999999999999999\r\n`), a verbatim string (`=29\r\ntxt:...\r\n`), a map (`%`), a set (`~`), an attribute (`|`) and a push (`>`). It writes an error as a simple error (`-`), never as a blob error (`!`). The `DEBUG PROTOCOL` command below sends one reply of each type. A malformed request, such as a bad length or a missing `\r\n`, gets the error `ERR Protocol error: ` and a short reason. The server then closes that connection. A bulk length above 512 MiB is a protocol error. Other clients are not affected. A request that ends early, because the client closed the connection, is dropped without a reply.

An unknown command gets `ERR unknown command 'NAME'`, where NAME is the command name as the client wrote it. A command with the wrong number of arguments gets `ERR wrong number of arguments for 'name' command`, with the name in lower case. An unreadable or out-of-range integer argument gets `ERR value is not an integer or out of range`. A bad option gets `ERR syntax error`.

## Commands

- `PING` replies `PONG`. `PING msg` replies with `msg` as a bulk string.
- `ECHO msg` replies with `msg` as a bulk string.
- `HELLO [protover [AUTH username password] [SETNAME name]]` with no argument replies with the connection's current protocol. With `protover` `2` or `3` it switches the connection to that protocol, and replies in the new protocol with a map of `server` (`rotom`), `version` (`0.1.0`), `proto` (the protocol now in use), `id` (the client id), `mode` (`standalone`), `role` (`master`) and `modules` (an empty array). In RESP2 the map is a flat array of the keys and values. Any other `protover` gets `NOPROTO unsupported protocol version`, and an unreadable one gets the integer error. The server has no users, so `AUTH` gets `WRONGPASS invalid username-password pair or user is disabled.` and changes nothing. `SETNAME` sets the client name, as `CLIENT SETNAME` does.
- `CLIENT ID` replies with the client id, an integer that is different for each connection. `CLIENT SETNAME name` replies `OK`. `CLIENT GETNAME` replies with the name as a bulk string, or a null if none is set.
- `DEBUG PROTOCOL type` replies with a fixed value of one RESP3 type, for a test of a client or a server. `type` is `string` (`Hello World`), `integer` (`12345`), `double` (`3.141`), `bignum` (`1234567999999999999999999999999999999`), `null`, `array` (`0`, `1`, `2`), `set` (`0`, `1`, `2`), `map` (`0` to false, `1` to true, `2` to false), `attrib`, `push`, `verbatim` (`txt`, `This is a verbatim\nstring`), `true` or `false`. For `attrib`, it first writes an attribute that maps `key-popularity` to the array `key:123`, `90`, and then the bulk string `Some real reply following the attribute`. For `push`, it first writes a push of `server-cpu-usage` and `42`, and then the bulk string `Some real reply following the push reply`. In RESP2, each value becomes the nearest RESP2 type: a double, a big number and a verbatim string become bulk strings, a set becomes an array, a map becomes a flat array of its keys and values with true as `1` and false as `0`, a boolean becomes an integer, an attribute is left out, and `push` gets `ERR RESP2 is not supported by this command`. An unknown `type` gets the syntax error.
- `QUIT` replies `OK` and closes the connection.
- `COMMAND` replies with an empty array. This lets `redis-cli` connect.
- `SET key value [EX seconds | PX milliseconds] [NX | XX]` stores the value and replies `OK`. `NX` sets only if the key is missing, and `XX` only if it exists. If the condition fails, it replies with a null bulk string and changes nothing. A `SET` without `EX` or `PX` removes any expiry on the key. `EX` and `PX` need a positive integer. Giving both `EX` and `PX`, or both `NX` and `XX`, is a syntax error.
- `GET key` replies with the value, or a null if the key is missing or expired.
- `MSET key value [key value ...]` replies `OK`. With an odd number of arguments, it gets the wrong-number error. `MGET key [key ...]` replies with an array that holds the value, or a null bulk string, for each key.
- `DEL key [key ...]` replies with the number of keys it removed. `EXISTS key [key ...]` replies with how many of the keys exist; a key named twice counts twice.
- `INCR key`, `DECR key`, `INCRBY key n` and `DECRBY key n` treat the value as a 64-bit signed integer, treat a missing key as 0, and reply with the new value as an integer. A value that is not an integer, or a result that would overflow, gets the integer error and changes nothing. These commands keep the expiry on the key.
- `APPEND key value` adds to the end of the value (it creates the key if missing) and replies with the new length. `STRLEN key` replies with the length in bytes, or 0 for a missing key.
- `EXPIRE key seconds` and `PEXPIRE key milliseconds` set an expiry and reply `1`, or `0` if the key is missing. A zero or negative time deletes the key at once. `TTL key` and `PTTL key` reply with the time left in seconds or milliseconds, `-1` if the key has no expiry and `-2` if it is missing. `TTL` rounds to the nearest second. `PERSIST key` removes the expiry and replies `1`, or `0` if the key is missing or has no expiry.
- `KEYS pattern` replies with an array of the matching keys, in any order. The pattern supports `*`, `?`, `[abc]`, `[a-c]`, `[^a]` and `\` to escape a character.
- `TYPE key` replies `string` or `none`, as a simple string.
- `DBSIZE` replies with the number of keys. `FLUSHALL` removes all keys and replies `OK`.

## Expiry

An expired key behaves as if it were missing in every command, as soon as its time has passed. The store also deletes expired keys in the background, so that memory does not grow without end. Time comes from a clock the store receives, so that tests of the store do not wait.

## Compatibility

`redis-cli` from Redis 7 works with the server, in RESP2 and in RESP3 (`redis-cli -2` and `redis-cli -3`). For each command and option above, the server gives the same reply as Redis 7 gives for the same arguments, in both protocols. The exceptions are the error messages and the `COMMAND` reply that this spec fixes, and any option that this spec does not list. For example, `redis-cli -p PORT SET k v` prints `OK`, and `redis-cli -p PORT GET k` then prints `v`.

## Tests with redis-cli

Redis 7, with `redis-server` and `redis-cli`, is on `PATH` when the server is tested. The tests run `redis-cli` against the server for every command and every option in this spec, once with `-2` and once with `-3`, and they check each reply, error and exit status. They include edge cases: missing keys, expired keys, binary values, overflow, wrong argument counts, bad options and each `DEBUG PROTOCOL` type. They also run `redis-cli --pipe` with thousands of pipelined commands, `redis-cli -x` to read a value from standard input, and several `redis-cli` processes at the same time. For the same arguments, the output of `redis-cli` against the server must equal its output against a real `redis-server`, except where this spec fixes a different reply. `redis-cli` 7 cannot print a big number or an attribute, so the tests read those two types with a raw socket and compare the bytes with this spec. A test fails, and does not skip, if `redis-cli` or `redis-server` is missing.
