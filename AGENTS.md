# Rules for agents in this repo

This file is for any agent that works here: Claude Code, Codex or another.
`CLAUDE.md` imports it. The README says what the project is and how to run it.

## Before you call a change done

Run these checks and fix what they report:

```
gofmt -l .                                   # must print nothing
go vet ./...
GOFLAGS=-buildvcs=false go fix -diff ./...   # must print nothing
go test -race ./...
go generate ./...                            # after you change event or graph types
cd ui && npm run build                       # type-checks the UI
```

Then review the change with the ponytail-review skill
(`.claude/skills/ponytail-review/SKILL.md`). Review the prose you wrote
(README, docs, comments, UI text, specs, commit messages) against the Orwell
rules below. Fix every Must fix and Should fix finding.

## At the end of each phase

A phase is not done until a new session with a different model has reviewed
its code and prose:

1. All the checks above pass.
2. Run `go run ./cmd/phasereview -phase phase-N -base <commit before the phase>`.
   The reviewer model from `guardrails.yaml` follows ponytail-review, checks
   Go against the modern Go guidelines, and checks prose against the Orwell
   rules. It writes `docs/reviews/phase-N.md`.
3. Fix every Must fix, Should fix and Prose finding. Run the review again
   until the verdict is "Ship."
4. Commit the review file with the phase.

## Evals

- Only `go run ./cmd/evalgen evals/<name>` writes the hidden tests, the
  reference answer and `assumptions.md` for an eval. It uses the `eval_author`
  model in `guardrails.yaml`, which must not be a model the factory builds
  with. `guardrails.yaml` refuses a config that breaks this rule.
- Do not edit hidden tests or references by hand or with a builder model. To
  change what an eval checks, change its `spec.md` and run evalgen again.
- Never show `hidden/`, `reference/` or `assumptions.md` to a factory run.

## Project rules

- The event log is the only state. Events record the runtime's decisions, so
  readers never repeat its rules.
- Do not edit generated files. `go generate ./...` writes
  `ui/src/gen/events.ts`, and `go run ./cmd/factory standards -o AGENTS.md`
  writes the standards block below. Tests fail if either one is out of date.
- Prefer the standard library to a new Go module. Pin exact versions of new
  npm packages, and choose versions that are at least two weeks old.

## Standards

These rules come from three pinned skills (see `standards/vendor/lock.json`). When they disagree, the first one wins:

1. The tests and the contract.
2. Ponytail's never-cut list: validation at trust boundaries, error handling that prevents data loss, security.
3. The modern Go guidelines. Skip one only if it would not compile or would change behavior, and say why.
4. Ponytail's smallest complete change.
5. Orwell, for prose only. Code, identifiers, commands and Go conventions (error strings start in lower case and have no final period) stay as they are.

### Modern Go (Go 1.27)

`go fix -diff ./...` must print nothing. It checks 25 of the guidelines. No tool checks these 29, so follow them yourself:

- `generic_methods` (Go 1.27): Use generic methods instead of package-level generic helper functions when the operation naturally belongs to the type itself.
- `json_v2` (Go 1.27): Use `encoding/json/v2` for new JSON code in Go 1.27+; leave existing `encoding/json` code unchanged unless migration is explicitly requested.
- `stdlib_uuid` (Go 1.27): Use the standard library `uuid` package instead of third-party libraries or custom UUID implementations when targeting Go 1.27+.
- `url_clone` (Go 1.27): Use the `URL.Clone` and `Values.Clone` methods from `net/url` to copy URLs and `URL` values instead of manual copying.
- `maps_keys_values_iter` (Go 1.23): Use `maps.Keys` or `maps.Values` directly as iterators instead of manually looping over a map.
- `slices_collect` (Go 1.23): Use `slices.Collect` to build a slice from an iterator.
- `slices_sorted` (Go 1.23): Use `slices.Sorted` to collect and sort iterator values in one step.
- `time_tick_gc` (Go 1.23): Use `time.Tick` when it fits; Go 1.23 can recover unreferenced tickers without requiring `Stop` for GC.
- `cmp_or` (Go 1.22): Use `cmp.Or` to pick the first non-zero value from a fallback chain.
- `http_servemux_patterns` (Go 1.22): Use method-aware `ServeMux` patterns and `r.PathValue` for path parameters.
- `clear` (Go 1.21): Use `clear(m)` to delete all map entries or `clear(s)` to zero slice elements.
- `slices_index` (Go 1.21): Use `slices.Index` to find the index of an element, returning `-1` when absent.
- `slices_index_func` (Go 1.21): Use `slices.IndexFunc` to find an element by predicate.
- `slices_sort_func` (Go 1.21): Use `slices.SortFunc` with `cmp.Compare` instead of `sort.Slice` for typed comparisons; replace `sort.SliceStable` with `slices.SortStableFunc`, because `slices.SortFunc` is not stable.
- `slices_max_min` (Go 1.21): Use `slices.Max` and `slices.Min` instead of manual loops over ordered values.
- `slices_reverse` (Go 1.21): Use `slices.Reverse` instead of a manual swap loop.
- `slices_compact` (Go 1.21): Use `slices.Compact` to remove consecutive duplicates in place.
- `maps_clone` (Go 1.21): Use `maps.Clone` instead of manual map iteration.
- `maps_delete_func` (Go 1.21): Use `maps.DeleteFunc` to delete map entries that match a predicate.
- `sync_once_func` (Go 1.21): Use `sync.OnceFunc` instead of `sync.Once` plus a wrapper closure.
- `sync_once_value` (Go 1.21): Use `sync.OnceValue` to memoize a computed value.
- `context_after_func` (Go 1.21): Use `context.AfterFunc` to run cleanup when a context is canceled.
- `context_timeout_deadline_cause` (Go 1.21): Use timeout and deadline contexts with causes when callers need to inspect the cancellation reason.
- `errors_join` (Go 1.20): Use `errors.Join` to combine multiple errors while preserving error matching.
- `context_cancel_cause` (Go 1.20): Use `context.WithCancelCause` and `context.Cause` when cancellation needs to carry an error cause.
- `strings_clone` (Go 1.18): Use `strings.Clone` to copy a string without retaining shared backing memory.
- `errors_is` (Go 1.13): Use `errors.Is(err, target)` instead of `err == target` so wrapped errors are handled correctly.
- `time_until` (Go 1.8): Use `time.Until(deadline)` instead of `deadline.Sub(time.Now())`.
- `time_since` (Go 1.0): Use `time.Since(start)` instead of `time.Now().Sub(start)`.

### Ponytail, lazy senior dev mode

You are a lazy senior developer. The best code is the code never written. You solve the whole problem with the least new code. End your reply with one or two lines: what you skipped or did not check, and any risk the user must know.

#### Before you write

Read the task and the code it touches. List every place your change must reach: callers, tests, fixtures, config, exports. Check what your change could break for users: data it would destroy or expose, callers that stop working. That is scope. Extra features are not.

#### The smallest complete change

Take the first option that fully works:

1. Does it need to exist? Skip features, options and flexibility nobody asked for, and name them in one line. A vague request ("build me X") gets the smallest version that does the core job.
2. Already in this codebase (a helper, component, service, pattern)? Use it the way the surrounding code does.
3. Standard library or a platform feature? Use it, unless the project has its own. A house component beats a native widget.
4. An installed dependency? Use it. Never add a dependency for a few lines.
5. Can it be one line a reader gets at a glance? One line.
6. Otherwise: the minimum code that works.

- Be lazy about the solution, never about the change itself: finish every part the task needs, including the callers, tests and fixtures your change breaks.
- No abstraction, wrapper, type conversion, option, config, boilerplate or "for later" code nobody asked for. Keep values in the form the platform already gives you. Deletion beats addition. Keep the structure the codebase already has: its layers, interfaces and conventions.
- The shortest working diff wins, once you know everything it must touch. A one-liner that needs decoding is not short.
- Comment only the why the code cannot show, in one line.
- Bug fix: before you edit, grep every caller of the function you touch, then fix the root cause once in the shared code.
- Code you move or merge keeps its error handling and validation.
- Between options of equal size, take the one that is correct on edge cases.
- Lazy code without its check is unfinished: new non-trivial logic (a branch, a loop, a parser, money or security, or a whole new script or app) leaves one small test or an assert-based self-check. Trivial changes need none.
- A shortcut with a known limit gets a code comment in this form: `shortcut: <the limit>, <when to upgrade>`.

Never cut: validation at trust boundaries, error handling that prevents data loss, security, accessibility, the calibration real hardware needs, anything the user asked for.

### Orwell Writing

#### Overview

Use Orwell's rules and ASD-STE100 Simplified Technical English (STE) as practical filters for clear, direct, and honest prose. Use STE by default for technical, instructional, business, and product prose. Apply the rules to both drafting and revision, but do not erase deliberate voice, character, rhythm, humor, or genre when the user clearly wants them.

STE has writing rules and a controlled dictionary. Use an approved word with its approved meaning when the dictionary is available. Do not claim strict STE conformance without checking the current ASD-STE100 issue and dictionary.

#### Core Rules

Remember these rules from "Politics and the English Language":

1. Never use a metaphor, simile, or other figure of speech which you are used to seeing in print.
2. Never use a long word where a short one will do.
3. If it is possible to cut a word out, always cut it out.
4. Never use the passive where you can use the active.
5. Never use a foreign phrase, a scientific word, or a jargon word if you can think of an everyday English equivalent.
6. Break any of these rules sooner than say anything outright barbarous.

#### ASD-STE100 baseline

For technical and instructional prose:

1. Use short sentences. Put one main action or statement in each sentence.
2. Use a clear subject and an active verb. Name the actor when the actor matters.
3. Use the same term for the same thing. Do not change a term only to avoid repetition.
4. Use familiar words with one precise meaning. Avoid idioms, slang, figurative language, and vague verbs.
5. Use a specific technical term when it is necessary for accuracy. Define it or link to its definition.
6. Keep noun groups short. Use prepositions to show relationships between terms.
7. Write procedures as direct instructions. State the condition, action, and expected result.
8. Use positive instructions when they are clear. State what the reader must do.
9. Use consistent American English spelling unless the user's style guide requires another variety.
10. Preserve code, commands, identifiers, product names, legal text, and required quotations. Do not simplify them silently.

When strict STE is not possible, keep the text clear and mark the terms or passages that need a domain-specific exception.

#### Workflow

When writing from scratch:

1. Identify the audience, purpose, and promised tone from the user's request.
2. Draft in concrete, direct English.
3. Remove stock phrases, dead metaphors, filler, pompous diction, needless abstraction, and avoidable jargon.
4. Prefer active verbs and clear subjects unless passive voice better serves emphasis, tact, suspense, or technical accuracy.
5. Keep necessary nuance; do not make prose crude, false, or flat just to make it short.
6. Apply the ASD-STE100 baseline. Check terms, sentence structure, instructions, and technical exceptions.

When revising existing text:

1. Preserve the user's meaning and any explicit tone or format constraints.
2. Cut words, clauses, and sentences that do no work.
3. Replace stale figures of speech with plain phrasing or a fresh, specific image.
4. Replace long, foreign, scientific, or jargon terms with everyday English when accuracy permits.
5. Convert passive constructions to active ones when the actor matters and is known.
6. Flag any remaining jargon, passive voice, or ornate phrasing that is necessary rather than silently removing important precision.
7. Run a final STE pass. Check that each technical term is consistent, each instruction states the required action, and each exception is intentional.

#### Creative Writing

For fiction, poetry, memoir, scripts, and lyrical prose, treat STE as a clarity aid, not a requirement that overrides the user's form. Keep intentional ambiguity, cadence, dialogue style, imagery, and character voice when they create a real effect. Remove only language that feels inherited, inflated, evasive, or lazy. Use strict STE when the user explicitly requests it, and note when that request conflicts with a creative effect.
